# D.A.M VPN for LG — этап 2: TUN с откатом

Статус 30.10.2026: план одобрен, скрипты готовы (`stage2/tv/`).

Цель: весь трафик ТВ (приложения, а не только `curl` через SOCKS5) идёт через Xray → Quattro.
Начинаем только по отдельному явному запросу владельца ТВ и после ответов на вопросы в конце.

## Что известно о ТВ (отчёт facts 30.10.2026)

- Ядро 5.4 aarch64, система 32-битная; TUN встроен (`CONFIG_TUN=y`, `/dev/net/tun` есть, интерфейсов tun нет).
- Сеть: только Wi-Fi `wlan0`, 192.168.1.146/24, шлюз 192.168.1.1; есть глобальный IPv6 и IPv6-маршрут по умолчанию.
- Правила маршрутизации IPv4 работают (`ip rule`); для IPv6 ядро их не поддерживает (`ip -6 rule` → «Address family not supported»).
- DNS: `/etc/resolv.conf` → ConnMan (127.0.0.1 и ::1), дальше роутер 192.168.1.1.
- `iptables` есть, таблицы не загружены; ConnMan: IPv4 DHCP, IPv6 auto, ручных DNS нет.
- Есть отдельный маршрут к одному внешнему IPv4 через роутер — чей, неизвестно; выяснить до начала.

## Схема (рекомендую)

1. **Один процесс Xray**, к конфигу этапа 1 добавляется вход `tun`: интерфейс `damvpn0`, адрес `10.233.0.1/30`, MTU 1500.
   Собственный трафик Xray привязан к `wlan0` (`autoOutboundsInterface: "wlan0"`), чтобы не уйти обратно в туннель.
2. **Без правки основной таблицы маршрутов.** Прежние «половинки» `0.0.0.0/1` + `128.0.0.0/1` (ProxyTune) не повторяем.
   Отдельная таблица 100 с одним маршрутом `default dev damvpn0` и правила с точными номерами:
   - `8991`/`8992` (UDP) и `8993`/`8994` (TCP): `to <DNS роутера>/32 ipproto … dport 53 lookup 100` — DNS в туннель;
   - `9000`: `to <локальная сеть> lookup main` — локальная сеть и SSH с Mac мимо туннеля;
   - `9001`: `to <IP сервера Quattro>/32 lookup main` — подстраховка от петли;
   - `9002`, `9003`: мультикаст `224.0.0.0/4` и `169.254.0.0/16` мимо туннеля (поиск устройств в сети);
   - `9004`: `lookup 100` — всё остальное в туннель.
3. **DNS** — без ConnMan и без правки `resolv.conf`: ConnMan спрашивает роутер, правила 8991–8994 уводят этот запрос
   в туннель, Xray передаёт его своему DNS (`port 53` → `dns-out`; запросы к 1.1.1.1 и 8.8.8.8 — через Quattro, только IPv4).
   Если `ip rule` на ТВ не понимает `dport`, DNS-правила не ставятся, и проверка покажет, что DNS идёт мимо.
4. **IPv6**: правил для IPv6 ядро не умеет, поэтому без мер IPv6-трафик пойдёт мимо туннеля (утечка).
   Рекомендую на время работы отключить IPv6 только на `wlan0` (`sysctl net.ipv6.conf.wlan0.disable_ipv6=1`) —
   это изменение до перезагрузки, откат его возвращает. Нужно ваше согласие: ТЗ этапа 1 sysctl запрещало.
5. **QUIC (UDP 443)** не блокируем: VLESS умеет UDP. Если видео будет тормозить — отдельное решение.

## Что изменится на ТВ (всё живёт до перезагрузки)

Интерфейс `damvpn0` (создаёт Xray), таблица 100, правила 8991–9004, `disable_ipv6` на `wlan0`, папка `/tmp/tvvpn`.
Не меняются: настройки ConnMan, `resolv.conf`, iptables, постоянные файлы, автозапуск.

## Откат

1. **Обычный** (`tvctl stop`): остановить Xray — ядро само удаляет `damvpn0` и все маршруты через него (таблица 100 пустеет);
   затем `ip rule del pref 8990 … 9009`, вернуть `disable_ipv6`, удалить `/tmp/tvvpn`;
   сравнить снимок (интерфейсы, маршруты, правила, DNS, sysctl) с сохранённым до запуска — должно совпасть.
2. **Автоматический («мёртвая рука»)**: при запуске взводится таймер на 5 минут, который выполняет откат сам,
   если вы не подтвердили работу командой `tvctl confirm`. Спасает, если пропал SSH.
3. **Аварийный**: перезагрузка ТВ — все изменения временные, после неё сеть как до запуска.
   Если ТВ не отвечает на пульт — выключить из розетки на 30 секунд.
4. Правила с точными номерами: откат удаляет только своё и ничего лишнего.

## Порядок

1. Только чтение: чей маршрут к внешнему IPv4; не перехватит ли ConnMan интерфейс `damvpn0`
   (`/etc/connman/main.conf`, список игнорируемых интерфейсов); поддерживает ли `ip rule` `ipproto` и `dport`.
2. Самопроверка новых скриптов на Mac (что можно проверить без ТВ).
3. На ТВ: снимок → запуск на 5 минут → проверки → откат → сверка снимка. Затем то же с подтверждением.
4. Проверки: `curl https://api.ipify.org` **без** прокси показывает IP Quattro; DNS идёт через туннель; IPv6 не утекает;
   SSH с Mac не рвётся; видео в приложении на ТВ идёт; после отката сеть совпадает со снимком; после перезагрузки — тоже.

## Вопросы к вам перед этапом 2

1. IPv6 на время работы VPN: отключать на `wlan0` (рекомендую) или оставить (часть трафика пойдёт мимо VPN)?
2. DNS через туннель по схеме выше — согласны?
3. Сервер для этапа 2 — тот же №48 «Швеция»?

## Решения (30.10.2026)

IPv6 на время работы выключаем на `wlan0`; DNS — через туннель по схеме выше; сервер — №48 «Швеция».

## Команды

```sh
cd ~/Documents/Codex/lg-tv-vpn/stage1/mac
./tvctl tun-config                      # уже собран 30.10 для №48
./tvctl push linux-arm32-v7a && ./tvctl tun-start && ./tvctl tun-check
./tvctl tun-confirm                     # в течение 5 минут после tun-start, иначе откат сам
./tvctl tun-stop                        # откат, сверка сети, удаление /tmp/tvvpn
```

Без Mac: `sh /tmp/tvvpn/rollback.sh` в SSH на ТВ или перезагрузка ТВ.

## Изменения после первых запусков (30.10.2026, по tun-diag)

- ConnMan отправляет свои DNS-запросы с сокета, привязанного к `wlan0`: правила 8991/8993 их не ловят (0 пакетов в туннель),
  и при поднятом туннеле ConnMan отвечал NXDOMAIN на www.youtube.com — YouTube: «код −105». Прямой запрос к роутеру
  уходит в туннель, и Xray через Quattro находит адреса (проверено дважды).
- Поэтому на время работы `resolv.conf` подменяется bind-монтированием только для чтения: `nameserver <роутер>`.
  Приложения спрашивают роутер напрямую → правило 8991 → туннель → DNS Xray. Откат снимает монтирование; перезагрузка — тоже.
- IPv6 больше не выключаем (`disable_ipv6` сбивал маршруты ConnMan до перезагрузки). Выход по IPv6 закрыт маршрутами
  `unreachable ::/1` и `unreachable 8000::/1`; локальный IPv6 работает; откат их удаляет. Старый способ — `IPV6_OFF=1`.
- В проверке исправлен поиск строк DNS в журнале: Xray пишет `tun-in -> dns-out` (маршрут по правилу), а не `>>`.

## Изменения после dns-facts (30.10.2026, ~18:20)

- Роутер сам отвечает NXDOMAIN на www.youtube.com — и без VPN (YouTube заблокирован на уровне DNS роутера или провайдера).
  1.1.1.1 напрямую не отвечает (заблокирован), 8.8.8.8 отвечает. NAT в ядре ТВ нет — перехват DNS файрволом невозможен.
- YouTube — веб-приложение в WebAppMgr: среда общая с системой, но resolv.conf он прочитал при запуске (::1, 127.0.0.1 → ConnMan),
  поэтому подмена resolv.conf ему не помогла. Подмену убрали.
- Теперь: Xray слушает DNS на адресе ТВ (`tunnel` на 192.168.1.146:53, только для самого ТВ, остальным — `blackhole`);
  на время работы ConnMan переключается на этот адрес (`connmanctl config <сервис> --nameservers 192.168.1.146`).
  Сокет ConnMan привязан к Wi-Fi, но адрес самого ТВ ему доступен. Ответы — встроенный DNS Xray (8.8.8.8, 1.1.1.1) через Quattro.
- Это настройка ConnMan, которая сохраняется. Откат и «мёртвая рука» возвращают прежнее значение; если питание пропало
  во время работы, `tvctl tun-stop` видит, что DNS ConnMan указывает на сам ТВ, и возвращает автоматический.
  Вручную — в меню ТВ: Сеть → Wi-Fi → дополнительные настройки → DNS автоматически.
